★ 핵심 총정리

시험·면접 전에 이것만은

7일 과정 전체에서 반드시 기억해야 할 내용을 주제별로 모았습니다. 자세한 설명은 각 날짜 이론에 있습니다.

★ 핵심 · 사고방식
  • 쿠버네티스에는 방법이 아니라 결과(원하는 상태)를 말한다 — 선언형.
  • 모든 기능은 원하는 상태 vs 현재 상태를 비교해 맞추는 조정 루프로 움직인다.
  • spec은 사람이 쓰는 주문서, status는 쿠버네티스가 채우는 배송 현황.
  • 변경은 파일에서 시작한다. 명령으로 바꾸거나 롤백했다면 파일도 맞춰야 다음 apply 때 되돌아가지 않는다.
★ 핵심 · 아키텍처
  • API 서버는 유일한 입구, etcd는 유일한 저장소(백업 = 클러스터 백업).
  • 스케줄러가 멈추면 새 Pod만 Pending. 마스터가 죽어도 이미 뜬 Pod는 계속 서비스한다.
  • 컨트롤 플레인은 Static Pod(/etc/kubernetes/manifests/)로 뜬다.
  • kubeadm init 직후 NotReady는 CNI가 없어서이며 정상.
★ 핵심 · Pod와 설정
  • 배포의 최소 단위는 Pod. 한 Pod의 컨테이너는 IP·볼륨·생명주기를 공유한다.
  • Pod는 고쳐 쓰지 않고 버리고 새로 만든다 → 이름·IP가 바뀐다.
  • 앱과 DB를 한 Pod에 넣지 않는다(따로 늘리고 따로 배포해야 하니까).
  • Secret의 base64는 암호화가 아니다. ConfigMap은 볼륨이면 자동 갱신, 환경 변수면 재시작 필요.
★ 핵심 · 연결은 라벨로
  • Service·Deployment는 Pod를 라벨 셀렉터로 그때그때 찾는다.
  • 라벨 한 글자만 틀려도 오류 없이 빈 결과 → Service 장애 1순위 원인.
  • version처럼 바뀌는 라벨은 selector에 넣지 않는다.
  • Service가 안 되면 EndpointSlice가 비었는지부터 본다.
★ 핵심 · 배치와 노드
  • nodeSelector·Affinity는 Pod가 노드를 고르고, taint는 노드가 Pod를 거부한다.
  • NoSchedule은 새 Pod만 막고, NoExecute는 기존 Pod도 쫓아낸다.
  • cordon = 새 Pod 차단, drain = cordon + 기존 Pod 축출. 다시 만드는 건 컨트롤러.
  • PDB는 drain 같은 자발적 중단만 막는다.
★ 핵심 · 워크로드 고르기
  • 같은 것 여러 개 → Deployment / 노드마다 하나 → DaemonSet
  • 이름·저장소가 고정돼야 함(DB) → StatefulSet
  • 한 번 하고 끝 → Job / 정해진 시각마다 → CronJob
  • 롤링 업데이트는 새 Pod가 Ready가 된 뒤 옛 Pod를 내린다. rollout undo는 파일을 고치지 않는다.
★ 핵심 · 안정성
  • liveness 실패 → 재시작, readiness 실패 → 트래픽 제외, startup → 기동 보호.
  • liveness에 DB 검사를 넣으면 재시작 폭풍.
  • requests = 배치 기준(예약석), limits = 실행 상한. CPU 초과는 느려지고, 메모리 초과는 OOMKilled(137).
  • HPA는 Pod 수만 늘린다. 노드에 자리가 없으면 Pending.
★ 핵심 · 저장소와 클라우드
  • PVC = 신청서, PV = 실제 창고, StorageClass = 자동 마련 업체.
  • EBS는 AZ를 못 벗어남 → WaitForFirstConsumer. 이때 PVC Pending은 정상.
  • MySQL 볼륨은 ext4의 lost+found 때문에 xfs.
  • 저장소 이전은 백업 → 전환 → 복원 → 검증, 이전 볼륨은 Retain으로 보존.

1. 쿠버네티스란

★ 공식 정의

쿠버네티스는 컨테이너화된 워크로드와 서비스를 관리하기 위한 이식성이 있고 확장 가능한 오픈소스 플랫폼으로, 선언적 구성과 자동화를 모두 지원합니다.

이름의 뜻

그리스어로 조타수·파일럿. 배(컨테이너선)의 키를 잡는 사람이라는 뜻입니다.

K8s

K와 s 사이 글자 8개(ubernete)를 숫자로 줄인 약어입니다.

출발

구글이 2014년 오픈소스로 공개. 구글의 15년 이상 대규모 운영 경험(Borg)과 커뮤니티 아이디어가 바탕입니다.

2. 배포 방식은 어떻게 바뀌어 왔나

전통적 배포물리 서버에 앱을 직접 설치
→
가상화 배포한 서버에 여러 VM
→
컨테이너 배포OS(커널)를 공유하는 가벼운 격리
시대방식문제 · 장점
전통적 배포물리 서버 한 대에 여러 앱자원 경계가 없어 한 앱이 자원을 독차지하면 다른 앱 성능이 떨어짐. 앱마다 서버를 따로 두면 비용 낭비.
가상화 배포하이퍼바이저 위 여러 VM, VM마다 자기 OS 전체앱 격리·보안 수준 향상, 자원 활용률과 확장성 개선. 대신 VM마다 OS가 있어 무겁다.
컨테이너 배포호스트 OS(커널)를 공유, 격리 속성을 완화VM보다 가볍고 빠름. 자체 파일 시스템·CPU 점유율·메모리·프로세스 공간을 가지며 클라우드·OS 배포판 간 이식 가능.
컨테이너가 인기 있는 이유 (공식 문서의 장점 목록)
  • 기민한 생성과 배포 — VM 이미지보다 컨테이너 이미지를 만들기 쉽고 빠름
  • 지속적인 개발 · 통합 · 배포(CI/CD) — 이미지가 불변이라 빠르고 쉬운 롤백
  • 개발과 운영의 관심사 분리 — 배포 시점이 아닌 빌드·릴리스 시점에 이미지를 만들어 인프라와 앱을 분리
  • 가시성(observability) — OS 수준 정보뿐 아니라 앱 상태와 신호까지 확인
  • 개발 · 테스트 · 운영 환경의 일관성 — 노트북에서처럼 클라우드에서도 동일하게 구동
  • 클라우드 · OS 배포판 간 이식성 — Ubuntu, RHEL, 온프레미스, 주요 퍼블릭 클라우드 어디서든
  • 애플리케이션 중심 관리 — 가상 하드웨어의 OS가 아닌 논리적 리소스로 앱을 실행
  • 느슨하게 결합된 분산 마이크로서비스 — 하나의 큰 단일 머신이 아닌 작은 독립 조각으로 동적 배포·관리
  • 리소스 격리 — 예측 가능한 앱 성능
  • 자원 사용량 — 고효율 고집적

4. 쿠버네티스가 아닌 것

쿠버네티스는 PaaS처럼 보이는 기능(배포·확장·로드 밸런싱)을 주지만 전통적인 올인원 PaaS가 아닙니다. 중요한 것은 사용자가 고르도록 남겨 둡니다.

⚠ 시험 단골 — "옳지 않은 것"의 정답 후보
  • 지원하는 애플리케이션 유형을 제한하지 않는다. 컨테이너로 돌릴 수 있으면 상태 유지·비유지·데이터 처리 모두 가능.
  • 소스 코드를 배포하지 않으며 애플리케이션을 빌드하지 않는다. CI/CD 워크플로는 조직의 선택.
  • 미들웨어·데이터베이스·캐시·스토리지 같은 애플리케이션 레벨 서비스를 기본 제공하지 않는다.
  • 로깅·모니터링·경보 솔루션을 강요하지 않는다(개념 증명용 통합과 메트릭 수집·노출 메커니즘만 제공).
  • 설정 언어(예: Jsonnet)를 제공하거나 강요하지 않는다. 선언적 API만 제공.
  • 기계 설정·유지보수·관리·자가 치유를 위한 포괄적 시스템을 제공하지 않는다.
  • 단순한 오케스트레이션 시스템이 아니다. A→B→C처럼 정해진 워크플로를 실행하는 대신, 독립적이고 조합 가능한 제어 프로세스들이 현재 상태를 원하는 상태로 계속 이끌어 간다. 그래서 중앙 통제가 필요 없고 견고합니다.

6. 노드 준비 — 왜 이 설정들이 필요한가

설정무엇을 위해빠뜨리면
overlay 모듈이미지 계층을 겹쳐 쓰기(OverlayFS)컨테이너 생성 자체가 실패

💡 쉬운 비유

브리지는 사무실 안 인터폰입니다. 같은 사무실끼리는 교환기를 거치지 않고 바로 연결됩니다. 그런데 "대표번호는 담당자에게 돌려라"(= Service) 규칙은 교환기에 있습니다. br_netfilter는 내선도 교환기를 한 번 거치게 만드는 설정입니다.

⚠ 주의

설정은 /etc/modules-load.d/ · /etc/sysctl.d/에 파일로 남겨야 재부팅 후에도 유지됩니다. modprobe·sysctl -w만 하면 재부팅 다음 날 이유 없이 고장 난 것처럼 보입니다.

cgroup 드라이버는 하나로 — 노드의 자원을 통제하는 주체가 하나여야 합니다. Ubuntu는 systemd가 그 역할이므로 containerd도 SystemdCgroup = true. 어긋나면 부하가 걸릴 때만 노드가 불안정해져 원인을 찾기 어렵습니다. 실습은 containerd 2.x(설정 형식 1.x와 다름 — 인터넷의 1.7용 조각을 붙이면 적용 안 될 수 있음).

API 서버도 Pod로 도는데, Pod를 띄우려면 API 서버가 필요합니다. 그래서 kubelet이 디렉터리의 YAML을 보고 직접 띄우는 예외 경로를 둡니다. kubectl get pods에 보이는 것은 그 그림자(미러 Pod)라 kubectl delete로는 지워지지 않고, 파일을 치워야 사라집니다. 이름은 <이름>-<노드이름>이 됩니다.

워커 join은 양방향 신뢰입니다. 워커는 --discovery-token-ca-cert-hash로 마스터를 확인하고, 마스터는 --token(기본 24시간 유효)으로 워커를 확인합니다. 토큰이 만료되면 kubeadm token create --print-join-command.

CNI는 Calico, 모드는 VXLAN — AWS VPC는 모르는 Pod 대역 패킷을 나르지 않으므로, Pod 패킷을 노드 패킷 안에 넣어(캡슐화) 보냅니다. 보안 그룹에서 UDP 4789가 막히면 다른 노드의 Pod와만 통신이 안 됩니다.

💡 쉬운 비유

VXLAN은 편지(Pod 패킷)를 봉투(노드 패킷)에 넣어 보내는 것입니다. 중간 우체국(VPC)은 편지 주소를 몰라도 봉투 주소는 알아서 배달됩니다.

★ 핵심 · control-plane taint는 그대로 둔다

node-role.kubernetes.io/control-plane:NoSchedule은 API 서버·etcd가 앱과 자원을 다투지 않게 하는 장치입니다. 지우면 앱 Pod가 마스터에도 배치되어 이후 실습 결과가 달라집니다.

💡 쉬운 비유

Pod는 같은 방을 쓰는 룸메이트입니다. 방(네트워크·볼륨)은 함께 쓰지만 옷장(파일 시스템)은 각자입니다. 이사도 같이 갑니다.

pause 컨테이너 — Pod마다 우리가 쓰지 않은 컨테이너가 하나 더 있습니다. 가장 먼저 떠서 네트워크 자리를 잡고, 가장 마지막에 지워집니다. 다른 컨테이너가 재시작해도 Pod IP가 유지되는 이유입니다. kubectl에는 안 보이고 노드에서 crictl pods로 보입니다. READY 수에도 포함되지 않습니다.

💡 쉬운 비유

pause는 주차 공간에 먼저 세워 두는 라바콘입니다. 차(앱)가 들어왔다 나가도 라바콘이 있는 동안 그 자리는 우리 자리입니다.

Pod 네트워크 모델 — 모든 Pod는 고유한 IP를 갖고, 클러스터 안에서는 NAT 없이 모든 노드의 모든 Pod와 통신합니다(CNI가 지키는 약속). 단, Pod IP는 고유하지만 영구하지 않습니다 — 재생성되면 바뀌므로 이름으로 고정된 주소(Service)가 필요합니다. hostPort는 한 노드에 그 포트를 쓰는 Pod가 하나뿐이라 권장하지 않습니다.

무엇을 한 Pod에 넣고, 무엇을 나눌까

"사람과 그림자" 관계인지 보면 됩니다. 아래 판별 질문에 하나라도 "아니오"면 다른 Pod입니다.

  • 이걸 3개로 늘리면, 다른 것도 3개가 되어야 하나? → 아니면 분리
  • 한쪽만 새 버전으로 배포하고 싶은 날이 올까? → 그렇다면 분리
⚠ 가장 흔한 실수

앱과 DB를 한 Pod에 넣는 것. 앱을 3개로 늘리면 DB도 3개가 되어 데이터가 갈라집니다. 쇼핑몰이 shop-web·shop-api·shop-db 세 Pod로 나뉜 이유입니다.

💡 쉬운 비유 — 구내식당 자리

nodeAffinity는 "창가 자리로 주세요", podAffinity는 "친구 옆으로", podAntiAffinity는 "저 사람과 다른 테이블로". required는 "그 자리 아니면 안 먹고 기다림", preferred는 "되면 좋고 아니면 아무 데나".

⚠ 주의
  • 이름의 IgnoredDuringExecution = 이미 실행 중인 Pod에는 소급 적용 안 함.
  • required podAntiAffinity는 노드 수 ≥ 레플리카 수일 때만. 아니면 남는 Pod가 Pending.

3. 배치 거부 — taint와 toleration

taint는 노드의 거부권, toleration은 Pod의 면역력(자격)입니다. 방향이 nodeSelector와 반대라서, 전용 노드는 둘을 짝으로 씁니다.

effect새 Pod이미 떠 있는 Pod사용 사례
NoScheduletoleration 없으면 거부그대로 유지DB 전용 노드
PreferNoSchedule되도록 피함(점수 깎기)그대로예비 노드

💡 쉬운 비유 — 병실

격리 병실(taint 노드)에는 백신 접종자(toleration 있는 Pod)만 들어갑니다. 그런데 백신은 '자격'이지 '목표'가 아닙니다. 접종자를 꼭 그 병실로 보내려면 "병실 지정 티켓"(nodeSelector)을 함께 줘야 합니다.

Equal vs Exists: Equal은 key·value·effect 모두 비교, Exists는 value를 보지 않음, 빈 operator: Exists는 모든 taint를 견딤(kube-proxy·calico-node 같은 시스템 DaemonSet용 — 앱에는 쓰지 않음).

쿠버네티스가 스스로 붙이는 taint: control-plane(마스터), unschedulable(cordon 시 — cordon은 결국 taint 한 장), not-ready·unreachable(노드 비정상 — 모든 Pod에 300초 toleration이 자동으로 붙어 약 5분 뒤 다른 노드로 옮겨짐).

📎 실습 클러스터의 전용 노드 패턴

cap-node1 = 라벨 tier=front(앱), cap-node2 = taint dedicated=db:NoSchedule(DB 전용, DB Pod에만 toleration). 격리는 확실하지만 앱이 한 노드에 몰려 그 노드가 멈추면 서비스도 멈춥니다(7일차 장애 실험에서 확인).

상태 있는 앱을 Deployment로 두면 평소엔 멀쩡하다가 노드 교체·스케일 순간 데이터가 깨집니다.

StatefulSet을 지워도 PVC는 기본으로 남습니다(Retain) — 다시 만들면 같은 데이터가 이어집니다.

Job · CronJob — 끝나는 작업
  • Job의 restartPolicy는 Never 또는 OnFailure만 가능. backoffLimit(기본 6) 넘으면 Failed.
  • CronJob schedule: "0 */2 * * *" = 분·시·일·월·요일. concurrencyPolicy: Allow(기본)/Forbid(겹치면 건너뜀)/Replace. 기본 시간대는 UTC → 한국 시각은 timeZone: Asia/Seoul.
  • 이력 보관 기본: 성공 3 · 실패 1. 완료 Job 자동 정리는 ttlSecondsAfterFinished.
⚠ 주의

완료된 Job의 manifest를 다시 apply해도 재실행되지 않습니다. 다시 돌리려면 Job을 삭제하고 다시 만듭니다.

💡 쉬운 비유

Deployment는 "항상 켜져 있어야 하는 프로그램", Job은 "실행하고 끝나는 스크립트", CronJob은 "crontab에 등록한 스크립트"입니다.

  1. DaemonSet은 노드마다 하나씩 자동 배치되며, replicas 필드가 없다.

  4. StatefulSet을 지워도 PVC는 남는다.
  5. Job은 한 번 끝나는 일이고, 완료된 Job은 다시 apply해도 재실행되지 않는다.
  6. Pod IP는 바뀐다. 그래서 Service가 필요하다.
  7. Service는 selector로 Pod를 그때그때 찾는다.
  8. ClusterIP는 내부 전용, NodePort는 모든 노드에 포트를 연다.
  9. 클러스터 DNS 덕분에 IP 대신 이름으로 연결한다.
  10. Service가 안 되면 EndpointSlice가 비었는지 먼저 본다.

⚠ 흔한 사고 두 가지
  1. liveness에 DB 연결 검사를 넣으면 DB가 잠깐 느려질 때 멀쩡한 앱이 모두 재시작하는 재시작 폭풍. liveness는 앱 자신만, 의존 대상은 readiness에서.
  2. 기동이 느린 앱에 startup 없이 liveness만 걸면 영원히 재시작.
startupProbe:            # 기동 보호 — 예산 = failureThreshold × periodSeconds = 5×24 = 120초
  httpGet: { path: /healthz, port: http }
  periodSeconds: 5
  failureThreshold: 24
livenessProbe:           # startup 성공 뒤 시작, 자기 자신만 검사
  httpGet: { path: /healthz, port: http }
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:          # 트래픽 판단 — DB까지 확인하는 경로
  httpGet: { path: /readyz, port: http }
  periodSeconds: 5
  failureThreshold: 2

startupProbe 설정 원칙: ① 예산 = 최악 기동 시간 × 1.5~2배 ② 주기는 짧게·횟수는 많게(5초×24회가 60초×2회보다 빨리 통과) ③ startup과 liveness는 같은 검사 ④ 트래픽 판단은 항상 readiness가 따로. initialDelaySeconds는 "무조건 N초 뒤에 검사"라서 빨리 떠도 기다리고 늦게 뜨면 재시작 루프에 빠지므로 startupProbe로 대체합니다.

재시작은 "새 컨테이너"다 — liveness 재시작은 같은 이미지로 컨테이너를 새로 만드는 것입니다. Pod 이름·IP·볼륨(emptyDir·PVC)은 남지만, 컨테이너 안에서 고친 파일은 사라집니다. 바꿔야 할 내용은 이미지·ConfigMap·볼륨처럼 컨테이너 밖에 둡니다. 직전 로그는 kubectl logs --previous.

💡 쉬운 비유

컨테이너 재시작은 같은 호텔 방에 새 손님이 체크인하는 것. 방 번호(Pod IP)와 금고(볼륨)는 그대로지만, 앞 손님이 방에 두고 간 물건(컨테이너 파일)은 청소되어 사라집니다.

LimitRange · ResourceQuota
  • LimitRange: 적지 않은 컨테이너에 기본값(defaultRequest·default)을 넣고, max를 넘으면 403 거부. 대상: Container / Pod / PVC.
  • ResourceQuota: requests·limits 합계, Pod·Service 개수, 스토리지 용량을 제한. CPU·메모리 쿼터가 걸리면 그 값을 적지 않은 Pod는 거부.
  • 쿼터 초과로 Pod가 안 만들어지면 사유는 Pod 목록이 아니라 ReplicaSet 이벤트(kubectl describe rs)에 남습니다.
용량 계획 (Capacity Planning)

쿠버네티스는 네임스페이스 하나의 Quota만 검사하고, 모든 Quota의 합이 클러스터 용량을 넘는지는 보지 않습니다. 계산 순서: ① 노드 1대의 Allocatable → ② 시스템 Pod·DaemonSet 고정분 빼기 → ③ 노드 수 곱하기 → ④ 여유분(롤링 maxSurge, N+1, HPA 최대치) 빼기 → ⑤ 네임스페이스에 Quota 나누기 → ⑥ LimitRange max ≤ 노드 1대 몫. 실습은 앱 몫이 약 1450m인데 shop Quota가 2000m라, HPA가 10개로 늘려도 5개만 뜨고 나머지는 Pending이 됩니다("Quota ≠ 노드 용량"을 보여 주는 장치).

3. HPA — 수평 자동 확장

HPA는 지표(기본 CPU)를 보고 Pod 개수를 자동으로 조절합니다. 15초마다 계산해 Deployment의 scale(replicas)만 바꾸고, 실제 Pod는 ReplicaSet이 만듭니다.

원하는 replicas = 현재 replicas × (현재 지표 / 목표 지표)     # 올림, maxReplicas에서 멈춤
# 예) 2개가 평균 CPU 100%, 목표 50% → 2 × (100/50) = 4개

kubectl autoscale deploy shop-api --cpu=50% --min=2 --max=5   # v1.36 표기(--cpu-percent는 옛 표기)
  • 사용률(Utilization)은 requests 대비 % → 대상 컨테이너에 requests가 반드시 있어야 함.
  • 늘릴 땐 즉시, 줄일 땐 기본 300초 지켜본 뒤(behavior.scaleDown.stabilizationWindowSeconds) — 출렁임(flapping) 방지.
  • 수평(HPA, 개수) vs 수직(VPA, 크기). 외부 이벤트(큐 길이) 기반·0개 축소는 KEDA. 같은 지표로 HPA와 KEDA/VPA를 동시에 걸지 않음.
⚠ 경고

HPA를 쓰는 Deployment manifest에 replicas를 남겨 두면 apply할 때마다 그 숫자로 되돌아갑니다. 그냥 지우고 apply하면 일시적으로 1개로 줄어들기 때문에, Lab08은 kubectl apply set-last-applied로 "이 필드는 더 이상 관리하지 않는다"고 알립니다.

★ HPA의 천장은 노드 용량

HPA는 Pod 개수만 정합니다. REPLICAS가 10이어도 노드에 requests만큼 자리가 없으면 새 Pod는 Pending(FailedScheduling: Insufficient cpu). HPA를 볼 땐 REPLICAS와 실제 Running 수를 함께 봅니다. 노드를 늘리는 건 Cluster Autoscaler·Karpenter(8일차).

💡 쉬운 비유

HPA는 손님 수를 보고 계산대 직원 수를 정하는 매니저입니다. 손님이 몰리면 바로 부르고, 한산해졌다고 바로 퇴근시키지 않고 잠시 지켜본 뒤 줄입니다.

5일차 핵심 문장

  1. liveness는 재시작, readiness는 트래픽 차단, startup은 기동 보호다.
  2. liveness에 외부 의존성을 넣으면 재시작 폭풍이 난다.
  3. requests는 배치 기준, limits는 실행 상한이다.
  4. CPU 초과는 조여지고, 메모리 초과는 즉시 종료된다.
  5. 아무 설정이 없는 Pod(BestEffort)가 가장 먼저 쫓겨난다.
  6. LimitRange는 개별 객체, ResourceQuota는 네임스페이스 총량이다. 둘 다 기존 Pod에 소급되지 않는다.
  7. HPA는 늘릴 땐 즉시, 줄일 땐 안정화 시간을 둔다.
  8. 진단은 describe의 Events에서 시작한다.
  9. 복구는 파일까지 고쳐야 끝난다.
  10. 컨테이너 재시작은 새 컨테이너다. 볼륨 밖에 쓴 파일은 사라진다.
  11. 느린 기동은 startupProbe로 기다린다(initialDelaySeconds는 쓰지 않는다).
  12. HPA는 Pod 수만 늘린다. 노드에 자리가 없으면 Pending이다.

  6. PVC는 "신청서", PV는 "실제 공간", StorageClass는 "자동 마련"이다.

  9. 반환 정책이 Delete면 PVC 삭제 시 데이터까지 사라진다.

IAM과 CSI · EBS CSI 동적 프로비저닝 · NFS→EBS 데이터 이전 · ALB 연결 · 장애 실험

클러스터를 클라우드와 잇는 날입니다. 저장소는 NFS에서 EBS 블록 스토리지로, 입구는 노드 포트에서 ALB로 옮깁니다.

1. CSI — 저장소를 끼우는 표준 콘센트

쿠버네티스는 AWS를 모르고, AWS는 Pod를 모릅니다. CSI(Container Storage Interface)는 저장소 제공자가 쿠버네티스 코드를 고치지 않고 연결하는 표준 플러그인 규격입니다. PVC가 들어오면 CSI 드라이버가 AWS API를 불러 볼륨을 만들고 · 붙이고 · 마운트합니다.

구성형태하는 일

CSI NodeDaemonSet노드에 붙은 디스크를 포맷하고 Pod 디렉터리에 마운트
CSIDriver · CSINode등록 객체설치된 드라이버와 노드별 등록 상태(kubectl get csidriver,csinode)
💡 쉬운 비유

CSI는 콘센트 규격입니다. 규격이 같으니 EBS든 NFS든 같은 PVC로 꽂아 씁니다. 다만 전기가 들어오려면(실제 AWS 자원을 만들려면) IAM이라는 출입 권한이 필요합니다.

⚠ IAM 권한이 없으면

PVC가 Pending에 머물고 ProvisioningFailed 이벤트가 반복됩니다. 자세한 원인은 CSI 컨트롤러 Pod 로그에. 실습은 노드 역할에 AmazonEBSCSIDriverPolicyV2를 붙이는 방식(운영에선 Pod 단위 권한 — 8일차 IRSA·Pod Identity).

관리형 쿠버네티스 · eksctl·애드온 · IRSA·Pod Identity · 외부 Secret · 노드 자동 확장 · Ingress+ALB

새 기술을 배우는 날이 아니라, 지금까지 배운 개념이 관리형 환경에서 어떻게 달라지는지 비교하는 날입니다.

⚠ 비용

EKS 클러스터·ALB·EBS는 시간당 과금됩니다. 실습이 끝나면 반드시 삭제 절차까지 완료합니다.

1. 관리형 쿠버네티스 — 책임 경계

Amazon EKS는 AWS가 컨트롤 플레인(API 서버·etcd·스케줄러·컨트롤러)을 대신 운영합니다. API는 표준과 같아 kubectl 사용법이 그대로입니다.

누가무엇을
AWS컨트롤 플레인 다중 AZ 운영, 백업·인증서·패치(사용자는 서버 접속 불가)
사용자노드 OS 패치·AMI 갱신·노드 그룹 크기, 애드온 버전, manifest, RBAC, 데이터 백업
💡 쉬운 비유

자체 구축은 직접 지은 집, EKS는 관리비 내는 아파트입니다. 배관(컨트롤 플레인)은 관리사무소가 고치지만 집 안 가구(워크로드)는 여전히 내 책임입니다. 관리형 노드 그룹은 렌터카, Fargate는 택시(DaemonSet·EBS 불가 같은 제약).

★ 가장 큰 기술적 차이

EKS 기본 네트워크(VPC CNI)에서는 Pod가 VPC의 실제 IP를 받습니다. Calico처럼 별도 Pod 대역을 쓰지 않습니다. 그래서 ALB가 Pod IP로 직접 보낼 수 있지만(target-type: ip), 서브넷 IP가 고갈될 수 있습니다.

2. eksctl과 애드온

eksctl은 설정 YAML 하나로 CloudFormation 스택을 만들어 VPC·컨트롤 플레인·관리형 노드 그룹·kubeconfig까지 준비합니다(약 15~20분, 그중 절반이 네트워크와 컨트롤 플레인). 애드온은 AWS가 버전을 검증해 패키징한 구성요소입니다.

  4. 그래서 ALB가 Pod IP로 직접(target-type: ip) 보낼 수 있다.
  5. 노드 역할 공유 대신 ServiceAccount 단위 권한(IRSA · Pod Identity)을 쓴다.
  6. EBS CSI는 EKS 애드온으로 설치·관리한다.
  7. gp3 · xfs · WaitForFirstConsumer 선택 이유는 EKS에서도 동일하다.
  8. 앱 manifest는 그대로 옮기고, 저장소와 입구만 바꾼다.
  9. EKS 현장 표준 입구는 Ingress + AWS Load Balancer Controller다.
  10. 삭제는 Ingress → PVC → 클러스터 순서로, 마지막에 콘솔 확인까지 한다.

YAML 읽기 워크시트

1일차 4교시 · 약 45분 · 명령 실행 없이 읽고 해석하기

목표: 실제로 쓸 manifest 5개(Namespace·ConfigMap·Pod·Service·Deployment)를 읽고, 필드 위치를 경로로 적고, 실수 파일 6개의 오류를 찾습니다. 이후 sed로 파일을 고치고 오류 메시지를 이해하는 눈을 기르는 연습입니다.

태스크 1 · YAML 문법

매핑(키: 값)·시퀀스(- 항목)·스칼라를 구분합니다. 따옴표 없는 yes/no/on은 참·거짓, 5000은 숫자로 읽힌다는 점이 핵심.

태스크 2 · 4대 필드 식별

다섯 manifest의 apiVersion·그룹·kind·이름·네임스페이스·본문(spec/data)을 표로 채웁니다. Namespace에는 namespace 필드가 없고(클러스터 범위), ConfigMap은 spec 대신 data, 다섯 번째 필드 status는 클러스터가 채운다는 것을 확인합니다.

태스크 3 · 경로와 연결 관계

경로 표기: 점(.)은 한 단계 아래, [0]은 목록의 첫 항목 → 예 spec.containers[0].image. Deployment의 이미지 경로는 spec.template.spec.containers[0].image. 오브젝트는 이름(configMapRef·secretKeyRef) 또는 라벨(selector)로 서로를 찾습니다.

태스크 4 · 오류 찾기 (8개)
파일오류발견 단계
E1탭 문자로 들여쓰기① YAML 문법
E2image가 리스트 항목 밖으로 들여쓰기 어긋남① YAML 문법
E3Pod에 apps/v1 + kind: pod 소문자(2개)② 스키마
E4containers 아래 - 누락(리스트가 아님)② 스키마
E5env 값 yes·5000에 따옴표 없음(2개)② 스키마
E6selector tier: api ≠ 템플릿 라벨 tier: web③ API 검증
★ 이 Lab의 핵심

모든 manifest는 apiVersion · kind · metadata · spec(ConfigMap은 data)으로 되어 있고, 오브젝트는 이름 또는 라벨로 서로를 찾는다. 오류는 ① YAML 문법 → ② 스키마 → ③ API 검증 순서로 걸린다.

💡 클러스터가 생긴 뒤 확인하는 법

kubectl explain pod.spec.containers.image(필드 설명), kubectl apply --dry-run=server -f 파일(만들지 않고 ②·③ 단계 오류 확인).

  2. /etc/modules-load.d/k8s.conf

    부팅할 때마다 자동으로 읽어 들일 커널 모듈 목록입니다.

    modprobe는 지금 한 번만 적용됩니다. 재부팅 뒤에도 유지하려면 이 파일이 있어야 합니다.

    이미지 레이어를 겹쳐 하나의 파일 시스템처럼 보여 주는 모듈입니다.

    containerd가 컨테이너 루트 파일 시스템을 만들 때 씁니다.

  4. br_netfilter

    리눅스 브리지를 지나는 패킷도 iptables 규칙을 거치게 합니다.

    0이면 노드가 라우터 역할을 못 해 다른 노드의 Pod와 통신할 수 없습니다. kubeadm 사전 점검도 실패합니다.

    /etc/sysctl.d/의 설정 파일을 모두 다시 읽어 즉시 적용합니다.

    재부팅 없이 바로 반영하기 위해서입니다.

  2. SystemdCgroup = true

    컨테이너 자원(cgroup)을 systemd가 관리하게 합니다.

    kubelet은 systemd 드라이버를 씁니다. 런타임과 드라이버가 다르면 자원 관리자가 둘이 되어 노드가 불안정해집니다(설치 후 Pod가 계속 재시작되는 대표 원인).

    오타 난 설정으로 재시작하면 containerd가 죽고 노드 전체가 멈춥니다. &&는 앞 명령이 성공해야 뒤를 실행합니다.

🔍 코드 해설 — 이 코드가 하는 일과 쓰는 이유

따라하기 버전의 실제 명령·manifest에서 핵심 줄만 골라 하는 일과 왜를 나란히 적었습니다.

코드 해설shop-web Pod — nginx + 네이티브 사이드카
apiVersion: v1
kind: Pod
metadata:
  name: shop-web
  namespace: shop
  labels:
    app: shop
    tier: web
spec:
  initContainers:
    - name: log-agent
      image: busybox:1.37
      restartPolicy: Always
      command: ["sh", "-c", "touch /var/log/nginx/access.log; tail -F /var/log/nginx/access.log"]
      volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
  containers:
    - name: nginx
      image: nginx:1.30-alpine
      ports:
        - containerPort: 80
      volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
  volumes:
    - name: logs
      emptyDir: {}
  1. apiVersion: v1 / kind: Pod

    어떤 API 그룹의 어떤 종류 객체인지 밝힙니다.

    API 서버는 이 두 줄로 어떤 스키마로 검사할지 정합니다. Pod·Service·ConfigMap은 core 그룹이라 v1만 씁니다.

  2. labels: app: shop, tier: web

    Pod에 이름표를 붙입니다.

    4일차의 Service(selector: tier=web)와 Deployment가 이 라벨로 Pod를 찾습니다. 라벨이 없으면 연결할 방법이 없습니다.

  3. initContainers + restartPolicy: Always

    앱보다 먼저 시작하고 끝나지 않는 네이티브 사이드카가 됩니다.

    로그 수집기가 먼저 떠 있어야 nginx의 첫 로그를 놓치지 않습니다. 종료할 때는 앱이 먼저 끝나 마지막 로그까지 수집됩니다.

  4. touch …; tail -F …

    로그 파일이 없으면 만들고, 계속 따라 읽으며 표준 출력으로 보냅니다.

    -F는 파일이 교체·재생성돼도 다시 열어 계속 읽습니다. 표준 출력으로 나가야 kubectl logs -c log-agent로 볼 수 있습니다.

  5. emptyDir: {} + 두 컨테이너의 같은 mountPath

    Pod가 살아 있는 동안만 있는 빈 폴더를 두 컨테이너가 함께 씁니다.

    Pod 안 컨테이너는 파일 시스템이 분리되어 있습니다. 공유하려면 볼륨을 명시적으로 같이 마운트해야 합니다.

  6. mountPath: /var/log/nginx (nginx 쪽)

    공식 nginx 이미지의 /dev/stdout 심볼릭 링크를 빈 폴더로 덮습니다.

    덮지 않으면 로그가 파일이 아닌 화면으로 나가 사이드카가 읽을 파일이 생기지 않습니다.

코드 해설ConfigMap · Secret 만들기와 주입

  --from-literal=APP_TITLE="SkillBoost Shop" --from-literal=DB_MODE=memory

            name: shop-config
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: shop-db-secret
              key: DB_PASSWORD
  1. --from-literal=KEY=VALUE

    키-값을 명령줄에서 바로 넣습니다.

    값이 짧을 때 YAML 파일 없이 빠르게 만드는 방법입니다. 파일 내용 전체를 넣을 때는 --from-file을 씁니다.

  2. secret generic … 'ShopDB#2026'

    일반(Opaque) Secret을 만듭니다. 값은 base64로 저장됩니다.

    작은따옴표로 감싸야 셸이 # 뒤를 주석으로 자르지 않습니다. base64는 암호화가 아닌 인코딩입니다.

  3. envFrom.configMapRef

    ConfigMap의 모든 키를 한 번에 환경 변수로 넣습니다.

    키가 늘어도 manifest를 고칠 필요가 없습니다.

  4. env.valueFrom.secretKeyRef

    Secret의 특정 키 하나만 골라 환경 변수로 넣습니다.

    비밀번호처럼 민감한 값은 필요한 것만 골라 넣는 것이 안전합니다. 이미지·YAML에 비밀번호를 쓰지 않아도 됩니다.

  5. (확인) echo ${#DB_PASSWORD}

    값 대신 길이(11)만 출력합니다.

    화면·로그에 비밀번호가 남지 않게 확인하는 습관입니다.

코드 해설command · args · $(VAR) 치환 연습
spec:
  restartPolicy: Never
  containers:
    - name: app
      image: busybox:1.37
      env:
        - name: GREETING
          value: "hello"
        - name: POD_NAME
          valueFrom:
            fieldRef:
              fieldPath: metadata.name
      command: ["echo"]
      args: ["$(GREETING)", "from", "$(POD_NAME)", "$HOSTNAME"]
  1. restartPolicy: Never

    한 번 실행하고 끝나면 다시 시작하지 않습니다.

    echo는 바로 끝납니다. 기본값 Always면 끝날 때마다 재시작해 CrashLoopBackOff처럼 보입니다.

  2. fieldRef: metadata.name (Downward API)

    Pod 자신의 정보(이름·노드·IP)를 환경 변수로 받습니다.

    앱이 API 서버에 묻지 않고도 자기 이름을 알 수 있습니다.

  3. command / args

    Docker의 ENTRYPOINT / CMD를 덮어씁니다.

    이미지를 다시 만들지 않고 실행 명령만 바꿀 수 있습니다.

  4. $(GREETING) vs $HOSTNAME

    $(VAR)는 쿠버네티스가 env에 정의된 값으로 치환합니다. $HOSTNAME은 셸 문법이라 셸이 없으면 글자 그대로 출력됩니다.

    출력은 hello from lab03-cmd $HOSTNAME입니다. ["sh","-c","echo $HOSTNAME"]처럼 셸을 거치면 둘 다 치환됩니다. 치환하는 주체가 다르다는 것이 핵심입니다.

📎 끝난 뒤 상태

shop-web·shop-api Pod가 없는 상태가 정상입니다(drain으로 사라지고 오후 Lab05-A에서 Deployment로 되살림). 노드 라벨과 cap-node2의 DB 전용 taint는 유지합니다.

태스크 1 · 노드 상태와 cordon

노드 3대의 Ready·unschedulable을 jsonpath/custom-columns로 한 번에 조회, --field-selector spec.nodeName=cap-node1로 노드의 Pod 조회. 워커 2대 cordon 상태에서 연습 Pod → Pending(unschedulable) → cap-node1만 uncordon하면 거기서 Running. 종료 시 두 워커 모두 스케줄 가능.

태스크 2 · 노드 라벨과 배치 선택

cap-node1 → tier=front, cap-node2 → disk=ssd. shop-web에 nodeSelector tier=front(실행 중 Pod의 nodeSelector는 못 바꾸므로 재생성). 없는 라벨 요구 → Pending 사유 확인, disk=ssd preferred affinity → 배치 확인, 실행 중 라벨을 지워도 Pod 유지(IgnoredDuringExecution) 후 라벨 복구.

태스크 3 · taint와 toleration

kubectl taint nodes cap-node2 dedicated=db:NoSchedule(유지). disk=ssd nodeSelector만 가진 lab04-db-test는 Pending → toleration 추가 후 cap-node2에서 Running. NoExecute 실험: Pod 3개(① 미허용 ② 30초 허용 ③ 무제한) + maintenance=true:NoExecute → ①즉시, ②약 30초 후 사라지고 ③은 남음 → 실험 taint 제거.

태스크 4 · cap-node1 정기 점검

옵션 없이 drain → 실패 사유 확인(이미 cordon됨) → 필요한 옵션만으로 node/cap-node1 drained → shop-web이 복구되지 않은 이유(컨트롤러 없는 Pod), CoreDNS가 다른 노드에 다시 생긴 이유(Deployment 소속) 설명 → uncordon.

🔍 코드 해설 — 이 코드가 하는 일과 쓰는 이유

따라하기 버전의 실제 명령·manifest에서 핵심 줄만 골라 하는 일과 왜를 나란히 적었습니다.

코드 해설노드 상태 한 줄 조회와 cordon

  1. {range .items[*]} … {end}

    노드 목록을 하나씩 돌면서 같은 형식으로 출력합니다(jsonpath 반복문).

    노드가 몇 대든 한 줄씩 깔끔하게 나옵니다.

  2. conditions[?(@.type=="Ready")]

    조건 배열에서 type이 Ready인 항목만 고릅니다(필터식).

    조건은 배열이라 순서가 바뀔 수 있어 인덱스([0])로 고르면 안전하지 않습니다.

  3. kubectl cordon

    노드에 unschedulable: true를 표시해 새 Pod만 막습니다.

    기존 Pod는 그대로라 서비스 영향 없이 점검을 준비할 수 있습니다.

  4. --restart=Never … -- sleep 3600

    Deployment가 아닌 단독 Pod를 만들고, -- 뒤를 컨테이너 명령으로 넘깁니다.

    --가 없으면 sleep을 kubectl 옵션으로 오해합니다.

  5. describe … | tail -3

    맨 아래 Events만 봅니다.

    Pending의 이유(0/3 nodes are available: … unschedulable)는 항상 Events에 적힙니다.

  6. drain --dry-run=client

    실제로 내보내지 않고 무엇이 축출될지만 보여 줍니다.

    운영 노드 점검 전에 영향을 먼저 확인하는 습관입니다.

  3. sed 's|^spec:|spec:\n nodeSelector:…|'

    파일의 spec: 줄 바로 아래에 nodeSelector를 끼워 넣습니다.

    구분자를 |로 써서 경로의 /와 충돌하지 않게 했습니다. 실행 중 Pod의 nodeSelector는 바꿀 수 없어 파일을 고친 뒤 삭제 → 재생성합니다.

    "되도록 ssd 노드"라는 선호입니다. 점수(1~100)에 가중치를 더합니다.

    조건에 맞는 노드가 없어도 Pending이 되지 않고 다른 노드에 배치됩니다. 반드시 지켜야 하면 required…를 씁니다.

  5. IgnoredDuringExecution

    배치 이후 노드 라벨이 바뀌어도 Pod를 옮기지 않습니다.

    라벨을 지워도 실행 중 Pod가 유지되는 것을 실습에서 확인합니다.

  6. matchExpressions operator: In

    키의 값이 목록 중 하나면 일치. 그 밖에 NotIn · Exists · DoesNotExist · Gt · Lt가 있습니다.

    Exists는 value와 상관없이 key만 맞으면 허용합니다.

  3. effect: NoExecute + tolerationSeconds: 30

    NoExecute taint가 붙으면 30초 동안만 머물고 축출됩니다.

    붙였던 taint를 제거합니다.

    라벨 삭제(disk-)와 같은 문법입니다.

    DaemonSet Pod는 축출 대상에서 뺍니다.

    DaemonSet Pod는 지워도 같은 노드에 다시 생기므로 drain이 끝나지 않습니다.

  6. --delete-emptydir-data

    emptyDir 데이터가 사라지는 것을 승인합니다.

    데이터 손실을 모르고 진행하지 않도록 명시적으로 요구하는 옵션입니다.

  7. --force

    컨트롤러 없는 Pod(직접 만든 Pod)도 지웁니다.

    이런 Pod는 지워지면 다시 생기지 않습니다. Lab04가 끝나면 shop-web·shop-api가 없는 이유입니다.

따라하기 버전의 실제 명령·manifest에서 핵심 줄만 골라 하는 일과 왜를 나란히 적었습니다.

코드 해설shop-api Deployment manifest
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
  namespace: shop
  annotations:
    kubernetes.io/change-cause: "v1 최초 배포"
spec:
  replicas: 2
  progressDeadlineSeconds: 120
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: shop
      tier: api
  template:
    metadata:
      labels:
        app: shop
        tier: api
        version: v1
    spec:
      nodeSelector:
        tier: front
      containers:
        - name: api
          image: ghcr.io/worldvit/skillboost-api:v1
  1. apiVersion: apps/v1

    Deployment·ReplicaSet·DaemonSet·StatefulSet은 apps 그룹입니다.

    Pod(v1)와 헷갈리기 쉬운 부분입니다. 틀리면 no matches for kind 오류가 납니다.

  2. kubernetes.io/change-cause

    이 버전을 왜 배포했는지 적는 어노테이션입니다.

    rollout history의 CHANGE-CAUSE 열에 표시됩니다. 예전 --record 옵션을 대신합니다.

  3. progressDeadlineSeconds: 120

    120초 안에 진행이 없으면 Progressing=False (ProgressDeadlineExceeded)로 표시합니다(기본 600).

    실패를 빨리 알아채기 위해서입니다. 쿠버네티스가 자동으로 롤백하지는 않습니다.

  4. maxSurge: 1 / maxUnavailable: 0

    원하는 개수보다 1개까지 더 띄울 수 있고, Available이 원하는 개수 아래로 내려가면 안 됩니다.

    "새 Pod가 Ready가 된 뒤에 옛 Pod를 내린다"는 순서가 되어 잘못된 이미지로 배포해도 기존 Pod가 계속 서비스합니다.

  5. selector.matchLabels (version 없음)

    이 Deployment가 관리할 Pod를 고르는 조건입니다. 만든 뒤 바꿀 수 없습니다.

    여기에 version을 넣으면 v2로 바꿀 때 selector도 바꿔야 해서 업데이트가 불가능해집니다. 변하지 않는 라벨만 넣습니다.

  6. template.metadata.labels

    새로 만들 Pod에 붙일 라벨입니다. selector의 라벨을 모두 포함해야 합니다.

    포함하지 않으면 API 서버가 selector does not match template labels로 거부합니다.

  7. template 아래가 바뀔 때만 롤아웃

    image·라벨·env가 바뀌면 새 ReplicaSet이 생깁니다.

    replicas만 바꾸면 같은 ReplicaSet의 개수만 조정됩니다(스케일).

    파일 안 여러 곳을 한 번에 바꿉니다.

    이미지·버전 라벨·변경 사유 세 곳을 같이 바꿔야 history와 라벨이 실제 버전과 맞습니다.

  2. kubectl diff -f

    지금 클러스터 상태와 파일의 차이를 보여 줍니다.

    git diff처럼 적용 전에 무엇이 바뀌는지 확인합니다. 실수로 다른 필드를 바꿨는지 잡아냅니다.

  3. rollout status --timeout

    롤아웃이 끝날 때까지 기다리고, 실패하면 0이 아닌 종료 코드로 끝납니다.

    스크립트·CI에서 배포 성공 여부를 판단하는 기준이 됩니다.

  4. rollout undo

    직전 ReplicaSet의 템플릿으로 되돌립니다. 되돌린 결과는 새 revision 번호를 받습니다.

    예: revision 2로 되돌리면 revision 4가 되고 목록에서 2는 사라집니다. 특정 번호는 --to-revision=N.

  5. (중요) 되돌린 뒤 파일도 수정

    undo는 클러스터만 바꿉니다.

    파일이 v3인 채로 다음에 apply하면 불량 버전이 다시 배포됩니다.

          operator: "Equal"
          value: "db"

    조건에 맞는 노드마다 1개씩 Pod를 둡니다.

    노드 수가 곧 Pod 수입니다. 노드를 추가하면 자동으로 따라 들어갑니다.

  2. tolerations: dedicated=db

    DB 전용 taint가 있는 cap-node2에도 들어가게 합니다.

    처음에는 toleration 없이 만들어 DESIRED 1을 보고, 추가 후 2가 되는 것을 확인합니다. 마스터는 control-plane taint 때문에 여전히 제외됩니다.

  3. fieldRef: spec.nodeName

    이 Pod가 실행되는 노드 이름을 환경 변수로 받습니다.

    로그에 "어느 노드의 에이전트인지" 남기기 위해서입니다.

  4. hostPath: /var/log/pods

    노드의 폴더를 컨테이너에 연결합니다.

    kubelet이 모든 Pod 로그를 이 경로에 씁니다. 로그 수집기는 노드 파일을 읽어야 하므로 DaemonSet + hostPath 조합이 전형적입니다.

  5. readOnly: true / type: Directory

    읽기만 허용하고, 경로가 이미 있는 폴더여야만 마운트합니다.

    노드 파일을 실수로 바꾸지 않도록 최소 권한으로 엽니다.

    DB는 "아무 Pod나"가 아니라 "0번 Pod"처럼 정확한 대상에 붙어야 합니다.

    이 StatefulSet의 Pod에 DNS 이름을 줄 Headless Service를 지정합니다.

    root 비밀번호를 무작위로 만들고 공개하지 않습니다.

    DB를 cap-node2에 고정합니다.

태스크 1 · shop-api ClusterIP Service

shop-api 자가 치유

Liveness · Readiness · Startup Probe — 모든 Probe는 포트 이름 http로 참조

태스크 1 · Liveness (/healthz, 5초·1초·3회)

적용 후 기본값으로 채워진 필드를 -o yaml로 확인. Pod 하나에 POST /api/chaos/hang(앱을 멈춤) → 1분 안에 RESTARTS +1, Events에 Liveness 실패·재시작 사유, logs --previous로 재시작 전 로그.

태스크 2 · Readiness (/readyz — DB 연결 포함, 5초·2초·2회)

shop-db Service selector를 잠시 바꿔 DB에 닿지 못하게(데이터를 잃지 않는 방법) → shop-api 0/1이지만 RESTARTS는 그대로, EndpointSlice 모두 ready=false, NodePort API 실패 → selector 복구하면 명령 없이 자동 회복.

태스크 3 · Startup

STARTUP_DELAY=20 + startupProbe 2초×5회(=10초 예산) → 새 Pod 재시작 루프, 하지만 옛 Pod가 서비스를 유지(maxUnavailable 0) → 예산을 30초 이상으로, STARTUP_DELAY=10 → 롤아웃 완료.

🔍 코드 해설 — 이 코드가 하는 일과 쓰는 이유

따라하기 버전의 실제 명령·manifest에서 핵심 줄만 골라 하는 일과 왜를 나란히 적었습니다.

코드 해설세 가지 Probe가 들어간 컨테이너 설정 (최종본)

  - name: api
    image: ghcr.io/worldvit/skillboost-api:v2
    ports:
      - name: http
        containerPort: 5000

      - name: STARTUP_DELAY
        value: "10"

      httpGet:
        path: /healthz
        port: http
      periodSeconds: 2
      failureThreshold: 15
    livenessProbe:
      httpGet:
        path: /healthz
        port: http
      periodSeconds: 5

    readinessProbe:
      httpGet:
        path: /readyz
        port: http
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2

    Probe가 포트 이름으로 대상을 찾습니다.

    컨테이너 포트 번호가 바뀌어도 Probe 세 곳을 고칠 필요가 없습니다.

  2. startupProbe (2초 × 15회 = 30초)

    앱이 처음 뜨는 동안만 검사합니다. 성공할 때까지 liveness·readiness는 시작하지 않습니다.

    기동이 느린 앱을 liveness가 "죽었다"고 오해해 재시작하는 것을 막습니다. 예산(periodSeconds × failureThreshold)이 기동 시간보다 짧으면 계속 재시작됩니다(실습의 10초 예산 실험).

  3. livenessProbe /healthz

    "프로세스가 살아 있나"를 5초마다 묻고, 3번 연속 실패(약 15초)하면 kubelet이 컨테이너를 재시작합니다.

    프로세스는 떠 있지만 멈춰 버린(hang) 상태를 자동 복구합니다. 실습의 /api/chaos/hang으로 확인합니다.

  4. timeoutSeconds: 1

    1초 안에 응답이 없으면 실패로 셉니다(기본 1).

    멈춘 앱은 응답을 아예 안 하므로 타임아웃으로 실패가 쌓입니다.

  5. readinessProbe /readyz

    "지금 손님을 받아도 되나"를 묻고, 실패하면 Pod를 EndpointSlice에서 뺍니다(재시작 없음).

    DB에 연결할 수 없을 때 재시작해도 해결되지 않습니다. 트래픽만 빼고 DB가 돌아오면 자동으로 다시 넣습니다.

  6. /healthz vs /readyz

    healthz는 자기 자신만, readyz는 의존성(DB)까지 확인합니다.

    liveness에 DB 검사를 넣으면 DB 장애 하나로 모든 API Pod가 재시작되는 연쇄 장애가 납니다.

    실제 장애를 기다리지 않고 Probe 동작을 재현합니다.

  2. events --field-selector involvedObject.name=…

    특정 Pod에 대한 이벤트만 시간순으로 봅니다.

    Liveness probe failed → Killing → Started 순서로 재시작 과정이 남습니다.

  3. logs --previous

    재시작되기 전 컨테이너의 로그를 봅니다.

    현재 컨테이너는 새로 시작해 원인 로그가 없습니다. 죽기 직전 로그는 이전 컨테이너에 있습니다.

  4. patch svc shop-db … selector tier=db-maintenance

    DB Service가 아무 Pod도 가리키지 않게 만들어 "DB 접속 불가"를 흉내 냅니다.

  5. endpoints[*].conditions.ready

    EndpointSlice 안 각 Pod의 ready 여부입니다.

    readiness 실패 시 Pod는 Running이지만 ready=false가 되어 트래픽에서 빠지는 것을 확인합니다.

    이것이 없으면 kubectl top이 오류를 내고 HPA의 TARGETS가 <unknown>입니다.

    JSON Patch로 args 배열 맨 끝(-)에 옵션 하나를 추가합니다.

    merge patch로 배열을 건드리면 배열 전체가 교체되어 기존 옵션이 사라집니다.

    kubelet 인증서 검증을 건너뜁니다.

    스케줄러가 노드를 고를 때 쓰는 예약량입니다. 100m = 0.1코어.

    노드의 Allocatable에서 requests 합계를 빼고 남은 곳에만 배치합니다. HPA 사용률의 분모이기도 합니다.

  5. limits (cpu 500m, memory 256Mi)

    넘을 수 없는 상한입니다.

    CPU는 넘으면 느려지고(스로틀링), 메모리는 넘으면 OOMKilled(exit 137)로 컨테이너가 재시작됩니다. 메모리는 나눠 쓸 수 없는 자원이기 때문입니다.

  6. QoS 클래스

    requests=limits면 Guaranteed, 일부만 있으면 Burstable, 아무것도 없으면 BestEffort입니다.

    노드 메모리가 부족하면 BestEffort → Burstable → Guaranteed 순서로 먼저 축출됩니다.

  1. LimitRange defaultRequest / default

    자원을 적지 않은 컨테이너에 requests·limits 기본값을 채워 넣습니다.

    누군가 resources 없이 배포해도 BestEffort Pod가 노드를 독점하지 않습니다. 채워진 값은 kubernetes.io/limit-ranger 어노테이션으로 확인합니다.

  2. LimitRange max

    컨테이너 하나가 요청할 수 있는 상한입니다.

    넘으면 Pod 생성 자체가 거부됩니다(Forbidden). Deployment라면 Pod가 안 생기고 ReplicaSet 이벤트에 FailedCreate가 남습니다.

  3. ResourceQuota hard

    네임스페이스 전체 합계의 상한입니다.

    한 팀이 클러스터 자원을 다 쓰지 못하게 합니다. 개별 컨테이너 상한(LimitRange)과 역할이 다릅니다.

  4. requests.cpu 등이 있는 Quota

    이 Quota가 있으면 모든 Pod가 해당 값을 반드시 적어야 합니다.

    그래서 LimitRange 기본값과 함께 씁니다. 그렇지 않으면 resources 없는 Pod가 모두 거부됩니다.

  5. services.nodeports: "2"

    NodePort Service 개수도 제한할 수 있습니다.

    30080·31080 두 개를 쓰므로 세 번째 NodePort는 거부됩니다.

    manifest와 last-applied 기록에서 replicas를 없앱니다.

    replicas가 남아 있으면 apply할 때마다 HPA가 늘려 놓은 Pod 수가 2로 되돌아갑니다. Pod 수의 주인을 HPA 하나로 정리하는 작업입니다.

  2. scaleTargetRef

    조정할 대상(Deployment shop-api)입니다.

    HPA는 Pod를 직접 만들지 않고 대상의 replicas 값만 바꿉니다.

  3. averageUtilization: 50

    Pod들의 평균 CPU 사용량이 requests의 50%를 넘으면 늘립니다.

    기준이 requests이므로 requests가 없으면 계산할 수 없습니다. 원하는 수 = ceil(현재 수 × 현재 사용률 / 목표 사용률).

  4. min 2 / max 5

    최소 2개는 유지하고 최대 5개까지만 늘립니다.

    최소값은 가용성, 최대값은 비용과 Quota 보호를 위해 둡니다.

  5. scaleDown.stabilizationWindowSeconds: 60

    줄이기 전에 60초 동안의 추천값 중 가장 큰 값을 씁니다(기본 300초).

    부하가 잠깐 줄었다 다시 오를 때 Pod 수가 들쭉날쭉(flapping)하지 않게 합니다. 실습에서는 관찰 시간을 줄이려고 짧게 잡았습니다.

★ 이 Lab의 핵심

CPU는 조여지고 메모리는 죽는다. Quota 거부 사유는 Pod가 아니라 ReplicaSet 이벤트에. HPA를 쓰면 manifest의 replicas를 안전하게 빼야 한다.

    컨테이너가 시작하자마자 오류로 끝나 재시작이 반복됩니다.

metadata:
  name: shop-route
  namespace: shop

    - matches:
        - path:

            value: /api
      backendRefs:
        - name: shop-api

        - path:
            type: PathPrefix
            value: /

  1. gatewayClassName: nginx

    이 Gateway를 실제로 구현할 컨트롤러(NGF)를 지정합니다.

    Gateway는 "입구가 필요하다"는 선언이고, 클래스가 "누가 만들어 줄지"를 정합니다. NGF는 이를 보고 shop-gateway-nginx Deployment·Service를 만듭니다.

  2. listeners: name http, port 80

    입구에서 받을 프로토콜과 포트입니다.

    HTTPRoute가 sectionName: http로 이 리스너에 연결됩니다.

  3. parentRefs

    이 라우트를 어느 Gateway(리스너)에 붙일지 정합니다.

    인프라 담당(Gateway)과 앱 담당(HTTPRoute)이 리소스를 나눠 관리할 수 있습니다. Ingress와의 가장 큰 차이입니다.

  4. PathPrefix /api

    /api, /api/products는 일치하지만 /apis는 일치하지 않습니다.

    경로를 / 단위 요소로 비교하기 때문입니다. 문자열 앞부분 비교가 아닙니다.

  5. 규칙 두 개 (/api, /)

    더 구체적인(긴) 경로가 우선합니다.

    /가 먼저 적혀 있어도 /api 요청은 shop-api로 갑니다. nginx의 location과 같은 개념입니다.

  6. backendRefs name/port

    트래픽을 보낼 Service와 포트입니다.

    Pod가 아니라 Service를 가리킵니다. weight를 붙이면 8:2 같은 비율 분배(카나리 배포)가 됩니다.

  7. (확인) Accepted / ResolvedRefs

    Accepted는 Gateway에 붙었는지, ResolvedRefs는 백엔드 Service를 모두 찾았는지입니다.

    다른 네임스페이스의 Service를 가리키면 ReferenceGrant 없이는 RefNotPermitted가 됩니다.

  1. q() { … }

    이름이 q인 셸 함수를 정의합니다. $1은 첫 번째 인자(SQL문)입니다.

    긴 접속 명령을 매번 치지 않고 q "SQL"로 줄입니다.

  2. echo "$1" | kubectl exec -i

    SQL을 표준 입력으로 Pod 안 mysql에 넘깁니다. -i가 있어야 입력이 전달됩니다.

    따옴표가 겹치는 문제 없이 어떤 SQL이든 넘길 수 있습니다.

  3. '…$MYSQL_PASSWORD…' (작은따옴표)

    작은따옴표 안의 변수는 노드 셸이 아니라 Pod 안 셸이 치환합니다.

    비밀번호는 Pod의 환경 변수에만 있으므로 노드에 비밀번호가 노출되지 않습니다.

  4. rc=$?; rm -f …; exit $rc

    mysql의 종료 코드를 저장해 두고, 임시 파일을 지운 뒤 그 코드로 끝냅니다.

    정리 작업 때문에 실패가 성공으로 바뀌지 않게 합니다.

  5. -N

    결과에서 열 이름(헤더)을 뺍니다.

    결과가 1처럼 값만 나와 스크립트에서 비교하기 쉽습니다.

  6. dbwait의 for … sleep 5

    5초 간격으로 최대 60번(5분) SELECT 1이 성공할 때까지 기다립니다.

    Pod가 Ready여도 MySQL 초기화가 덜 끝났을 수 있습니다. 준비됐는지 직접 물어보는 것이 정확합니다.

    워커 두 대에만 읽기·쓰기를 허용합니다. sync는 디스크에 쓴 뒤 응답합니다.

    DB 데이터는 응답 후 유실되면 안 되므로 sync를 씁니다. 대역 전체를 열지 않는 최소 허용입니다.

    mysql 이미지가 쓰는 사용자 UID 999에게 폴더를 줍니다.

    NFS는 숫자 UID로 권한을 확인합니다. 기본 root_squash 때문에 root로는 쓸 수 없어 DB를 999로 실행합니다(runAsUser: 999).

  3. PV에 namespace 없음

    PV는 노드처럼 클러스터 범위 리소스입니다. PVC는 네임스페이스에 속합니다.

    관리자가 PV(실제 저장소)를 준비하고, 앱 팀은 PVC(사용 신청서)만 작성하는 역할 분리입니다.

  4. persistentVolumeReclaimPolicy: Retain

    PVC를 지워도 PV와 데이터를 남깁니다.

    DB 데이터를 실수로 지우지 않기 위해서입니다. 동적 프로비저닝 기본값은 Delete입니다.

  5. storageClassName: ""

    동적 프로비저닝을 쓰지 않겠다는 표시입니다.

    비워 두지 않으면 기본 StorageClass가 있을 때 새 볼륨을 자동으로 만들어 버립니다.

  6. volumeName: shop-db-pv

    이 PVC를 특정 PV에 직접 지정해 묶습니다.

    비슷한 PV가 여럿 있어도 의도한 PV에 붙습니다. 용량·accessModes가 맞아야 Bound가 됩니다.

  7. mountOptions: nfsvers=4.1, hard

    NFS 4.1로 마운트하고, 서버가 응답 없으면 오류 대신 계속 재시도합니다.

    soft 마운트는 일시 장애 때 쓰기 오류를 내 DB 파일이 깨질 수 있습니다.

  8. ReadWriteOnce vs ReadWriteMany

    RWO는 한 노드에서만, RWX는 여러 노드에서 동시에 읽기·쓰기입니다.

    shop-db는 RWO, CronJob과 shop-web이 함께 쓰는 리포트 볼륨은 RWX로 만듭니다.

코드 해설EBS CSI와 gp3 StorageClass
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
allowVolumeExpansion: true
parameters:
  type: gp3
  csi.storage.k8s.io/fstype: xfs
  1. provisioner: ebs.csi.aws.com

    이 클래스의 볼륨을 EBS CSI 드라이버가 만듭니다.

    드라이버가 PVC를 보고 AWS API로 EBS 볼륨을 생성·연결합니다. 노드 역할에 AmazonEBSCSIDriverPolicyV2 권한이 필요한 이유입니다.

  2. volumeBindingMode: WaitForFirstConsumer

    Pod가 노드에 배치될 때까지 볼륨 생성을 미룹니다. 그동안 PVC는 Pending입니다.

    EBS는 한 가용 영역(AZ)에서만 붙습니다. 미리 만들면 Pod가 다른 AZ 노드에 배치될 경우 붙일 수 없습니다.

  3. reclaimPolicy: Delete

    PVC를 지우면 PV와 실제 EBS 볼륨도 삭제됩니다.

    연습 볼륨이 남아 비용이 나가지 않게 합니다. 중요한 데이터는 Retain을 검토합니다.

  4. allowVolumeExpansion: true

    PVC의 용량을 나중에 늘릴 수 있게 합니다.

    DB 데이터가 커질 때 볼륨을 새로 만들지 않고 확장합니다(줄이기는 불가).

  5. type: gp3 / fstype: xfs

    EBS 볼륨 종류와 포맷할 파일 시스템입니다.

    gp3는 gp2보다 저렴하고 성능을 따로 정할 수 있습니다. MySQL은 xfs를 권장합니다.

  6. fsGroup: 999 (StatefulSet)

    마운트한 볼륨의 그룹 소유권을 999로 바꿉니다.

    새 EBS 볼륨은 root 소유라 999로 실행하는 MySQL이 쓸 수 없습니다. fsGroupChangePolicy: OnRootMismatch는 이미 맞으면 다시 바꾸지 않아 재시작이 빠릅니다.

    eksctl이 읽는 설정 파일입니다(쿠버네티스 리소스가 아님).

    명령 옵션을 길게 나열하지 않고 파일로 남겨 재현할 수 있게 합니다.

  2. withOIDC: true

    클러스터의 OIDC 공급자를 IAM에 등록합니다.

    IRSA(ServiceAccount에 IAM 역할 연결)의 전제 조건입니다. Pod가 노드 역할이 아닌 자기 역할로 AWS API를 호출합니다.

    EKS Auto Mode를 쓰지 않고 노드 그룹을 직접 관리합니다.

    실습에서 노드·애드온 구성을 눈으로 확인하기 위해서입니다.

    AWS가 관리하는 필수 구성요소입니다.

    kubeadm에서 직접 설치했던 Calico·CoreDNS·kube-proxy·EBS CSI를 EKS에서는 애드온으로 받습니다. vpc-cni는 Pod에 VPC의 실제 IP를 줍니다.

  5. autoApplyPodIdentityAssociations

    애드온에 필요한 IAM 권한을 Pod Identity로 자동 연결합니다.

    EBS CSI 같은 애드온이 노드 역할 권한 없이도 동작합니다.

  6. managedNodeGroups / labels tier=front

    AWS가 관리하는 워커 노드 그룹과 노드 라벨입니다.

    기존 manifest의 nodeSelector: tier=front를 그대로 쓰기 위해 같은 라벨을 붙입니다.
